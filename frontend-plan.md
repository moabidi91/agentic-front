# Front (exploitation) — plan

Ce document n'appartient pas au process ADR du backend (piloté par les autres agents sur `agentic-local-app/decisions.md`) : c'est le carnet de décisions de la partie front "exploitation", développée à part, sans toucher au code backend. Déplacé depuis `agentic-local-app/frontend-plan.md` vers son propre dossier (`hexarq-hive/` à l'origine, renommé `agentic-front/` une fois le nom d'application devenu configurable — voir plus bas) pour ne pas se mélanger avec les docs du backend.

## Statut

Phase maquettes (Design Components), pas encore d'implémentation. Canvas Claude à jour : https://claude.ai/artifact/BM8TgxFcFNHX5GyZAu5BJT (accès restreint au compte propriétaire — à partager depuis le menu Share de la page si besoin de le montrer à quelqu'un d'autre).

Écrans couverts : **Welcome** (choix du nom et de l'icône par l'utilisateur, avec aperçu en direct — le tout premier écran) → **Sign in, étape 1** (identité + modèle + credentials) → **Sign in, étape 2** (dossier de travail + skills + réglages avancés — séparée de l'étape 1, voir "Sign in en deux étapes" ci-dessous) → Connecting (progression de connexion ; guide navigable en 6 cartes, uniquement à la toute première authentification) → Chat (vue simple, avec contrôle de session pendant le traitement) ↔ Debug (supervision live, avec vue Diagramme du plan) ↔ History (explorateur d'événements) → Event detail (message in / message out) → pop-in 401 (renouvellement de jeton). En complément, deux écrans de référence/admin accessibles depuis le **menu utilisateur** (avatar, en haut à droite de Chat/Debug/History/ces deux écrans) plutôt que dans le fil principal : **State machine reference** (machines à états réelles + info de cycle) et **Live database** (inspection + vidage de la base locale).

Identité : **configurable par l'utilisateur**, pas de nom de produit figé dans le code (voir "Branding configurable" ci-dessous). Palette violet + teal (inspiration bancaire, jamais nommée dans aucun fichier).

Pour le détail technique (composants, état, surface API attendue du backend), voir [implementation-spec.md](implementation-spec.md).

## Décisions retenues

- **Stack** : TypeScript + React (Vite) pour le code front ; **Tauri** (pas Electron) pour l'empaquetage desktop — même code React, accès API OS natif (sélecteur de dossier, lecture du nom d'utilisateur système).
- **Auto-détection de l'utilisateur** : lue côté backend (`getpass.getuser()` / `%USERNAME%` / `$USER`), exposée via un futur endpoint du type `GET /whoami`. Pré-remplit le champ "User ID" (badge "Auto-detected"), reste éditable — ce champ devient l'identifiant de conversation.
- **Sélection modèle / transport** : liste de modèles sur l'écran de connexion (pas de valeur auto-sélectionnée), alimentée par le backend à partir des implémentations de transport détectées/configurées (registre `transport.provider`, ADR-020 côté backend : `generic_http`, `templated_http`, `fake`, ou un plugin). Choisir dans la liste active le provider + codec (ADR-021) correspondant.
- **Flag "credentials requis" par modèle** : selon le modèle/transport choisi, le champ Access token doit s'afficher ou non — certains transports gèrent l'authentification eux-mêmes (ex. un mock de dev, ou un provider qui embarque déjà son jeton), d'autres en ont besoin explicitement. Décision : ajouter un flag (proposition : `requires_credentials: bool`) sur la définition backend de chaque transport/modèle (même registre qu'ADR-020), exposé au front dans la même réponse que la liste des modèles disponibles. Le front n'a pas à deviner ; il affiche ou masque le champ token selon ce flag. **Pas encore fait côté backend** — c'est une demande à discuter avec l'équipe qui porte ADR-020 (ADR-025 potentiel). Démontré dans la maquette (`Main.dc.html`) : 3 modèles d'exemple, 2 avec `Token required`, 1 sans (`No credentials`, mock/dev) ; sélectionner un modèle affiche/masque le champ token en direct.
- **Sign in en deux étapes (nouveau)** : l'écran de connexion initial (identité + modèle + dossier de travail + skills + effort + réglages avancés, tout sur un seul écran) débordait verticalement une fois tous les champs affichés — bug d'affichage remonté en retour utilisateur. Corrigé en scindant en deux écrans : `Main.dc.html` (étape 1 — User ID, modèle, credentials) puis `Setup.dc.html` (étape 2 — dossier de travail, skills, réglages avancés affichés directement, sans accordéon à déplier), chacun avec un lien retour vers l'écran précédent et un badge "Step 1 of 2" / "Step 2 of 2". `Main.dc.html` gagne aussi un lien retour vers `Welcome.dc.html` (l'écran de config initiale), qui manquait.
- **Menu utilisateur (avatar) — reconfiguration & Reset (nouveau)** : sur chaque écran principal après connexion (Chat, Debug, History, et les deux écrans de référence ci-dessous), l'avatar en haut à droite ouvre un menu déroulant qui devient le point d'entrée unique pour tout reconfigurer sans repasser par le flux de connexion complet : identité & icône de l'app (renvoie vers `Welcome.dc.html`), modèle & transport (renvoie vers `Main.dc.html`), la référence machine à états, la base de données live, puis — séparé par un trait, en rouge — **Reset configuration**, qui ouvre une confirmation avant de renvoyer vers `Welcome.dc.html`. Remplace/complète l'ancien Reset "icône dans la barre du haut" mentionné plus bas (même sémantique d'interruption de session, mais accessible de façon cohérente partout, pas juste depuis Chat).
- **Carrousel de connexion enrichi (nouveau)** : le guide de première connexion (`Connecting.dc.html`) passe de 4 à 6 cartes. Les deux nouvelles expliquent (a) les états possibles d'une conversation en un coup d'œil (chips NEW → ACTIVE → RUNNING_PLAN → READY → COMPLETED, plus la possibilité de tomber à tout instant sur INTERRUPTED) et (b) les fonctionnalités de contrôle mises en avant cette itération : interruption à tout moment, vue diagramme du plan, journal d'audit chaîné par hash, nom/icône personnalisables. Volontairement simplifié par rapport à la vraie machine à états (qui a 11 états, voir plus bas) — le carrousel reste un teaser d'onboarding ; l'écran `StateMachine.dc.html` (voir plus bas) est la référence complète et exacte.
- **Interruption et message en attente pendant le traitement (nouveau)** : sur `Chat.dc.html`, pendant qu'une réponse/plan est en cours de traitement, deux nouveaux contrôles apparaissent : un bouton **Stop** à côté d'Envoyer (interrompt la session en cours, reflète `RUNNING_PLAN → INTERRUPTED → READY`), et la possibilité de taper et envoyer un nouveau message sans attendre — la zone de saisie l'accepte, avec un indice explicite sous le composeur ("A message sent now is queued — applied once the current cycle finishes, unless you interrupt."). Décision de principe validée avec l'utilisateur : le comportement cible est soit la mise en file (le message est pris en compte à la fin du cycle en cours), soit — si le backend le permet — l'interruption immédiate avec priorité donnée au nouveau message de l'utilisateur. Lequel des deux est réellement supportable dépend de ce que le backend peut faire ; **à trancher avec l'équipe backend**, voir [implementation-spec.md](implementation-spec.md) §5.
- **Vue live de la base + vidage (nouveau)** : nouvel écran `LiveDatabase.dc.html`, accessible depuis le menu utilisateur, qui montre en lecture seule les trois tables de la base locale — sessions, events, audit log (avec la note "chaîne vérifiée, aucun trou, aucune entrée réécrite") — avec un compteur de lignes par table et un indicateur "live". Une action destructive **Clear database** (bouton rouge, confirmation obligatoire qui prévient explicitement que même les sessions `RUNNING_PLAN` seraient supprimées, action irréversible) permet de repartir d'une base vide en démo/dev.
- **Écran de référence machine à états & cycle (nouveau)** : nouvel écran `StateMachine.dc.html`, accessible depuis le menu utilisateur, qui documente à l'écran les quatre machines à états réelles du backend (conversation — 11 états —, plan, tâche, fenêtre de contexte) avec leurs transitions exactes, plus un panneau latéral fixe donnant les infos du cycle courant (`cycle_id`, `cycle_type` : discovery / execution / clarification / resume) et le budget de session (`max_cycles`, `max_plans`, `max_total_duration_ms`) avec sa consommation actuelle. Construit à partir de `agentic-local-app/spec-v1.1.md` §5.1–5.4 et §4.1 pour rester fidèle à la vraie spec plutôt qu'une simplification — répond à la fois à la demande d'un "écran info cycle / machine à états" et sert de documentation vivante pour l'équipe.
- **Sélection de skills** : sur l'écran Sign in (étape 2 désormais), un champ optionnel "Skills" — comme le dossier de travail, pas obligatoire — où l'utilisateur choisit des fichiers de skills à mettre à disposition du modèle pour la session (liste de puces avec suppression + "Add skill"). Démontré dans la maquette avec 2 skills d'exemple présélectionnés (`release-checklist`, `db-migration-guide`) et un bouton pour en ajouter d'autres. **Pas encore de contrat backend** pour référencer/transmettre ces fichiers de skills — voir la demande détaillée dans [implementation-spec.md](implementation-spec.md).
- **Niveau d'effort** : un contrôle "Effort" (icône altère, Low / Med / High) dans les réglages avancés (étape 2 du sign in), qui se traduit en une consigne envoyée au modèle dans le protocole d'échange — par exemple, pousser à paralléliser davantage (plus de threads/workers), dans la limite de ce que permet la machine. Décision : c'est une information à ajouter au message envoyé au modèle (`user_request` ou équivalent), pas un simple réglage d'affichage — donc ça nécessite un contrat côté backend. **Pas encore fait côté backend**, voir [implementation-spec.md](implementation-spec.md) pour la proposition.
- **`working_space`** : dossier de travail choisi par l'utilisateur sur l'écran de connexion, injecté dans le message utilisateur comme `working_space`, matérialisé en dossier temporaire et nettoyé automatiquement une fois la tâche terminée. Concept introduit côté front — à rapprocher du chantier ADR-024 (scratch dir / `AGENTIC_SCRATCH_DIR`) en cours côté backend ; pas encore réconcilié entre les deux équipes.
- **Vue Diagramme du plan** (écran Debug) : à côté de la liste des tâches, un toggle "List / Diagram" affiche le plan en cours sous forme de graphe — une carte par tâche (id, résumé en langage clair, statut), reliées par des flèches selon leurs dépendances (`depends_on`). **Ça ne demande rien de nouveau côté backend** : la structure du plan (`execution_plan`, `depends_on` par tâche) et les statuts (`ExecutionTracker`) existent déjà dans le protocole — c'est uniquement une deuxième présentation, côté front, des mêmes données que la liste.
- **Écran "Connecting"** : écran entre Sign in (étape 2) et Chat, qui matérialise la vraie séquence de connexion (validation du token → création de session → premier appel au modèle). Sur la toute première authentification de l'utilisateur, cet écran affiche en plus un guide en 6 cartes (voir "Carrousel de connexion enrichi" ci-dessus), navigable manuellement (flèches + puces) et qui avance aussi tout seul ; le bouton "Continue to chat" est centré sous les puces du guide, pas dans la colonne de gauche (retour utilisateur pris en compte). Aux connexions suivantes, état minimal (spinner + checklist), sans guide. Reste à trancher : où persister "c'est la première authentification" (préférence locale au poste, ou flag côté compte utilisateur backend) — actuellement représenté dans la maquette par une simple prop `firstRun`, pas encore une vraie donnée persistée.
- **Branding configurable** : le nom de l'application et son icône ne sont **plus figés** — c'est l'utilisateur final qui les choisit, sur un nouvel écran `Welcome.dc.html` placé **avant** l'écran Sign in (le tout premier écran de l'app). Déroulé : un bref message le temps de "récupérer l'environnement" (spinner ~1 seconde), puis un message d'accueil direct et professionnel ("We've retrieved your information. Let's start by choosing the name and icon that suit you."), puis le choix lui-même — un nom principal, un petit label (badge), et une icône parmi six propositions (Pulse — neutre, par défaut —, Concentric Hex, Orbit Node, Hex Monogram, Honeycomb, Facet), avec un **aperçu en temps réel** de l'affichage réel (panneau de connexion + barre d'en-tête de l'app), qui se met à jour immédiatement à chaque sélection. Un bouton "Continue" centré et prominent mène ensuite à Sign in. Toutes les autres maquettes reçoivent ce choix via deux props, `appName` / `appLabel` (valeurs par défaut `"Console"` / `"OPS"` si l'utilisateur ne personnalise rien), et n'affichent plus aucun nom de produit codé en dur. **Ne nécessite rien côté backend** pour la démonstration en maquette (état purement front, non persisté entre écrans séparés) ; pour une vraie implémentation, il faudra décider où persister ce choix (préférence locale, type fichier de config, ou un futur profil utilisateur côté backend) — non tranché, voir [implementation-spec.md](implementation-spec.md).
- **Fin de session** : au lieu d'un arrêt automatique, un choix explicite ("Continue chatting" / "New session") après réception de la réponse finale, plus une préférence "When a session completes" (Ask each time / Continue automatically / Start new automatically) dans les réglages avancés. L'application elle-même ne s'arrête jamais, quel que soit ce choix.
- **Reset** vs **suppression de session** : le Reset (désormais dans le menu utilisateur, voir ci-dessus) interrompt la conversation en cours (`user_interrupt` → `INTERRUPTED` → `READY`) puis efface la configuration locale (retour à `Welcome.dc.html`) ; la suppression (dans la liste des sessions) retire une session de l'historique côté UI — deux actions distinctes.
- **Empaquetage / lancement** : un script `.bat` unique doit démarrer d'un coup le serveur backend (`agentic-app serve`) et l'app desktop Tauri, pour un lancement en un clic sous Windows. Deux approches possibles, pas encore tranchées :
  1. le `.bat` lance les deux process séparément (backend en arrière-plan, puis l'exécutable Tauri) ;
  2. le binaire Tauri embarque le serveur Python comme process "sidecar" qu'il démarre lui-même au lancement, et le `.bat` se contente de lancer l'exécutable Tauri.
  Le choix dépend de comment le serveur Python sera distribué (venv embarqué, binaire PyInstaller, etc.) — point à faire avec l'équipe backend avant de coder le launcher.
- **Langue de l'interface** : anglais uniquement, sans exception, sur tout ce que voit l'utilisateur. (Les docs de ce dossier restent en français : ce sont des notes d'équipe, pas de l'UI.)

## Ouvert / pas encore fait

- Implémentation réelle (scaffolding React + Vite + Tauri) : pas commencée — voir [implementation-spec.md](implementation-spec.md) pour le périmètre.
- Branchement avec le backend (endpoints réels, flux SSE live pour l'onglet Debug, `/whoami`, liste des transports disponibles + flag credentials, contrat skills, contrat effort) : pas commencé — dépend d'ADR-018 (API pour un front, flux live SSE) déjà accepté côté backend, et de plusieurs besoins pas encore côté backend (credentials, skills, effort, `working_space`).
- **Faisabilité du message envoyé pendant un traitement en cours** (nouveau) : à confirmer avec l'équipe backend si un `user_request` peut être accepté et mis en file pendant `WAITING_MODEL_RESPONSE`/`RUNNING_PLAN`/`ROTATING`, et si une interruption-puis-priorité (message pris en compte immédiatement après `INTERRUPTED → READY`) est réaliste sans perdre le fil de la conversation. **[besoin backend]**
- **Endpoints de lecture pour la vue live de la base** (nouveau) : la maquette `LiveDatabase.dc.html` montre des données statiques d'exemple ; il faut un moyen réel de lister sessions / events / audit log (lecture seule) et un endpoint (ou une action volontairement gardée) pour vider la base en dev/démo. **[besoin backend]**
- Persistance du choix nom/icône (Welcome) : où le stocker entre deux lancements de l'app — pas tranché (local uniquement, ou remonté au backend).
- Démo vidéo de la maquette : demandée, pas encore livrée en tant que fichier vidéo — cette session n'avait pas d'accès navigateur authentifié à claude.ai pour enregistrer un clic-à-clic. En attendant, [presentation-speech.md](presentation-speech.md) sert de support pour une démo live du canvas (mode Play, écrans liés).
